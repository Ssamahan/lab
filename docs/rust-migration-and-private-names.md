# Rust replacement and private patient-name project

This is a plan, not a completed rewrite or a working name-sync system. The current production app and existing Supabase project remain unchanged.

## Goals and limits

- Build a separate Rust/WebAssembly browser application, retaining a static GitHub Pages deployment and offline use. Rust cannot make network latency, browser rendering, startup, or storage take zero milliseconds. A WebAssembly build can even be slower to download or start than JavaScript. Measure on the actual phone and network before claiming improvement.
- The phone currently has pending register changes. Never clear browser storage, reset, import over, overwrite, or switch that device to the replacement as a migration shortcut. The existing standard register export does **not** include the separate patient-name store.
- Keep the repository public and all credentials out of it. Only a public Supabase publishable key belongs in browser code; it is not a secret and never substitutes for access control. Never put a service-role/secret key, database password or user password in the repository, app bundle or chat.

## Replacement plan

1. **Baseline.** Measure cold and warm startup, time to usable screen, screen interaction time, downloaded bytes, memory and sync duration, on a representative phone and connection. Separate rendering, CPU, local storage and network time. Use synthetic data and record methodology; do not export real patient information for benchmarking.
2. **Inventory and contract.** The existing application is a static JavaScript site with a service worker, a register in `labSystems.v1`, separate names in `labSystems.names.v1`, and a pending counter in `labSystems.pending.v1`. Inventory the 15 modules, all settings, audit trail, manifests, imports/exports, leave overlay, offline queue and Android wrapper. The wrapper configuration must be reviewed separately; do not assume its current remote URL is correct. Treat every data format and observable behavior as a compatibility requirement until explicitly changed.
3. **Isolated prototype.** Build the Rust UI as a separate, non-production application on a separate origin/path with synthetic fixtures. Evaluate binary size, WebAssembly initialization, compatibility and offline caching against the baseline. No direct access to the live register, no user credentials and no automatic writes. Prefer ordinary web standards for printing and accessible UI. Do not claim Rust alone improves security.
4. **Data migration.** Design and test versioned, reversible conversion of *copies* of the register, names, pending changes, sync metadata and manifests, including corrupt/missing storage, conflicts, interruptions and storage exhaustion. The old app and its data must remain usable. Cross-origin storage is isolated: a new path or origin cannot be assumed to read another site's browser data. Never mark pending work sent unless the server confirms it; timeout does not establish whether a write arrived. Design explicit conflict handling before enabling writes. Rehearse using synthetic data and verified secure backups; ordinary register export alone is insufficient for names.
5. **Feature parity.** Implement and test samples and manifest printing, stock, schedules/leave, quality/EQA, training and manually entered ticket routes, reporting/PBF, staff/security and sync. Test role-scoped contacts and auditing. Distinguish route suggestions from recorded travel; retain no-key map links and funding chart. Preserve screen accessibility and mobile/offline behavior. Compare signed plans without silently applying edits or dropping leave overlays.
6. **Security and deployment.** Use actual server-verified identity and restrictive server-side policies, not the existing local app login as proof of identity. Run adversarial tests using public and anonymous tokens. Add automated build, tests, accessibility and bundle/performance budgets. Test service worker upgrades and rollback without changing stored data. Keep the existing site as the production fallback. Cut over only after verified backups, user approval and end-to-end tests on the actual devices; no real-data production migration during the prototype.

No performance target can be honestly guaranteed before a baseline. Set budgets after measuring, and report cold/warm results, device, connection, and any failed tests.

## New Supabase project: what Kelvin does

1. Sign in to the Supabase dashboard and choose **New project** in the appropriate organization. Give it a recognizable name such as `ruli-lab-private-names`. Keep the existing project; do not delete, pause, reset, or copy its tables over it.
2. Choose a region approved by the hospital for patient data. Supabase region choices are fixed; the current project is in the EU, not Rwanda. Confirm data-residency, transfer and backup requirements with the hospital before storing real names. Choose the project size/plan after checking its costs and backup/restore capabilities.
3. Generate a strong database password and store it in the hospital's password manager. Do not paste it into the app, public repository or chat. Wait for the new project to finish provisioning.
4. In **Authentication → Users**, create or invite a real user for Kelvin using an email account he controls. Set the password privately in Supabase or via the invite; do not share it in chat. Do not use anonymous sign-ins to protect names. If other staff need access later, provision separate identities and permissions rather than sharing Kelvin's password. Set a strong password and enable MFA where supported and appropriate.
5. Tell the agent the **project name or project reference** (the project ref is not a secret). Make sure the new project is available to the connected Supabase integration. Do not send a password, service-role/secret key, access token, or patient names.
6. The developer must then implement a separate name store and synchronization: server-side RLS must deny `anon` and anonymous authenticated sessions, grant access only to explicitly authorized user IDs, and verify with real permitted and denied sessions. Do not store names in the public register. Test offline queues, retries, conflicts, account changes, backups and recovery with synthetic data first. The site login is currently local and is not the Supabase login; the implementation must obtain and use a real Supabase session without storing passwords in the shared register. Only after those checks and your approval should existing device-held names be copied; do not delete the local originals.

Creating the project and account alone does **not** sync, recover, encrypt end-to-end, or back up patient names. Supabase transport security, encryption at rest, server-side authorization and provider backups are distinct from end-to-end encryption. A name visible in the app or a manifest is also visible to someone with access to the unlocked device or printout.

## Existing exposure and pending work

The old project has permissive public read policies, and an older history snapshot contains some patient names. The new project will not automatically secure or erase that old history. A separately reviewed incident/remediation and retention plan is needed; do not blindly delete history or remove access in a way that destroys records or breaks existing devices. The current Supabase timeout and three pending device changes remain unresolved, independently of this plan.

## Setup status (2026-11-07)

The new `ruli-lab-private-names` project has an append-only `public.patient_name_entries` table and a private allowlist. One existing non-anonymous account was authorized. The schema is documented in `supabase/private-names.sql`; the individual authorization is deliberately not hard-coded in the public repository. It is installed only on the new project.

RLS is enabled. Database-level synthetic tests, run inside rolled-back transactions with simulated JWT claims, allowed the authorized identity to read and insert, and returned no rows to an unapproved identity and an anonymous-session claim. The anonymous role has no table select/insert privilege, and authenticated clients have no update/delete privilege. These tests are not an actual browser sign-in or end-to-end sync test. No synthetic rows were retained and no real names were copied.

A separate client has been implemented for v6.9.120. It signs in with the private Supabase Authentication account, keeps credentials/tokens in memory only, and syncs names via an atomic compare-and-append function. A local edit schedules a sync while signed in; connection errors leave names on the device, and conflicting values require review. Private sign-in is separate from the current client-side Kelvin app login and must be repeated after a page reload or token expiry. On the Referred Samples screen select **Private names**, use the private project's Authentication email and password, and select **Sign in & sync names**. The first sign-in attempts to send the names currently held on that device; it never clears the old local store.

`private-names-atomic.sql` is applied after `private-names.sql` on the new project only. SQL policy checks and synthetic client tests passed. Real account/browser sign-in, networking on the user's devices, backup/recovery, and the complete deployment still need verification. Ordinary register backup does not include local names. The existing public project's history and its exposure remain unchanged. Cloud and browser storage are not end-to-end encrypted; an authorized user, project administrator, compromised app, or person with access to an unlocked device may access names.
